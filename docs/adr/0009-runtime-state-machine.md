# ADR-0009：由 Coordinator 统一管理 Runtime 状态转换

- Status: Accepted（负责人已确认 D01 至 D06）
- Date: 2026-10-31
- Deciders: ForgeRL 项目负责人
- Scope: 第二周 Runtime 状态机；后续接入 Coordinator

## Context

ForgeRL 需要在启动前检查配置和插件，在初始化后执行训练，并处理 Checkpoint、停止和故障。不同阶段允许执行的操作不同。如果调用方可以随意修改状态，系统可能跳过校验、在初始化失败后开始训练，或在结束后继续分配任务。

项目设计第 9 节已经定义正常主路径和故障恢复方向，并要求由 Coordinator 统一执行全局状态转换、生成 RuntimeEvent。但启动失败、终态、重复转换、停止边界及事件生成接口尚未完全明确。

第二周先实现可在 CPU 上独立验证的状态机。测试可以扮演 Coordinator，不要求提前实现 Worker 管理、真实 Checkpoint 或自动恢复。

本文件区分两类内容：

- **既有约束**：来自项目设计和 ADR-0003，作为实现边界。
- **已确认决策**：D01 至 D06 的负责人结论是实施依据，备选方案保留用于解释取舍。

## Decision

### 1. 区分状态、转换规则和事件

| 概念             | 回答的问题                       | 例子                           |
| ---------------- | -------------------------------- | ------------------------------ |
| RuntimeState     | 一次运行现在处于什么阶段？       | RUNNING                        |
| 状态机           | 从当前状态进入目标状态是否合法？ | RUNNING 可以进入 CHECKPOINTING |
| RuntimeEventType | 已经发生的事实属于哪一类？       | TRAIN_STEP_COMPLETED           |
| RuntimeEvent     | 哪次运行、何时、发生了什么？     | 某次训练 Step 完成的具体记录   |

状态机维护当前状态并执行转换约束；事件保存已经发生的事实，供日志、指标和观察者使用。两者共同描述一次转换，但不重复承担控制职责。

事件与状态变化不是一一对应：

- 多次 TRAIN_STEP_COMPLETED 可以发生在同一个 RUNNING 阶段内。
- WORKER_HEARTBEAT 通常不改变全局运行状态。
- 进入 CHECKPOINTING 表示进入保存阶段，不表示 Checkpoint 已经写入成功。
- 收到 WORKER_FAILED 后，由 Coordinator 根据错误策略决定是否改变全局状态。

第二周不采用从事件历史重放并推导当前状态的事件溯源架构。事件不是另一个可以任意写入全局状态的入口。

### 2. 状态机的作用对象与标识

**既有约束：全局状态机描述一次 Run，不描述操作系统进程的生死。**

| 标识或信息       | 表达的对象                   | 当前情况与边界                                            |
| ---------------- | ---------------------------- | --------------------------------------------------------- |
| run_id           | 一次运行的身份               | RuntimeEvent 已有字段；同一次运行的事件共用该值           |
| worker_id        | Run 内的逻辑 Worker 身份     | RuntimeEvent 已有可选字段；不能假设它就是 PID             |
| event_id         | 一条事件的身份               | RuntimeEvent 已有字段，不是 Run 或 Worker 的身份          |
| PID              | 当前主机上的一个操作系统进程 | 仅用于进程管理和诊断；现有 RuntimeEvent 没有专用 PID 字段 |
| RuntimeState     | Run 当前阶段                 | 是状态值，不是身份标识                                    |
| RuntimeEventType | 事件类别                     | 是类别，不是身份标识                                      |

一个 Run 可以由 Coordinator、多个 Worker 等多个进程共同执行。CPU Mock 可以全部运行在同一进程内。逻辑 Worker 与操作系统进程不保证一一对应。

逻辑 Worker 的关联键可使用 `(run_id, worker_id)`。PID 会被操作系统复用，不能替代长期运行标识。后续如需区分 Worker 重启前后的实例，应在进程管理 ADR 中定义实例标识或启动代次；不能只依赖 PID。

全局状态变化事件建议令 worker_id=None。若转换由某 Worker 故障触发，可在约定的 payload 字段中记录关联 Worker；不要把“全局状态属于谁”和“故障涉及谁”混为一谈。

从 Checkpoint 恢复时是否沿用 run_id、是否增加运行尝试标识，留给恢复与 Checkpoint 设计。本 ADR 不为这些未实现的接口添加字段。

### 3. 职责与依赖方向

**既有约束：全局状态转换由 Coordinator 统一执行，Worker 不得自行修改全局状态。**

- Coordinator 执行或协调实际工作，根据结果请求状态转换。
- 状态机判断转换是否合法、维护当前状态，并按决策 D05 产生转换事件。
- 插件和 Worker 执行任务并上报结果、健康信息或错误。
- 日志和指标消费者读取事件，不成为第二个全局状态写入者。

状态机不调用插件工厂，不加载模型，不保存权重，不释放 GPU，不启动 Worker，也不执行自动恢复。进入某个状态不会自动触发这些工作。

例如，VALIDATING 进入 INITIALIZING 时，Coordinator 已确认参数和能力检查通过；状态机检查阶段顺序，不能仅凭枚举值证明校验工作确实成功。

第二周使用单线程、串行调用模型，不增加锁、进程队列或后台事件发布。后续并发接入时，由 Coordinator 将转换请求串行化。

### 4. 状态的含义

下表以项目已有状态集合为基础；FAILED 的资源清理边界由 D02 决定，故障与恢复的允许来源由 D04 决定。

| 状态          | 含义                                     |
| ------------- | ---------------------------------------- |
| CREATED       | Run 对象已创建，尚未开始校验             |
| VALIDATING    | 正在检查配置、插件参数和本次运行能力     |
| INITIALIZING  | 正在创建并初始化运行资源                 |
| RUNNING       | 已具备执行正常训练工作的条件             |
| CHECKPOINTING | 正在执行本版本中的 Checkpoint 阶段       |
| STOPPING      | 正在停止分配新工作并清理资源             |
| FINISHED      | 本次运行正常完成，包括正常清理           |
| DEGRADED      | 发现影响正常运行的故障，正常任务分配受限 |
| RECOVERING    | 正在执行有明确成功条件的恢复操作         |
| FAILED        | 本次运行以失败结果终止；清理边界见 D02   |

RUNNING 是准许正常工作的阶段，不代表每个 Worker 此刻都在执行计算。CHECKPOINTING 是本版本的全局阶段；以后若支持后台保存，需要重新评审是否使用独立子状态。

### 5. 正式状态转换规则

项目已定义的正常转换如下。调用方负责确认“触发条件”已经满足。

| 当前状态      | 目标状态      | 触发条件                           |
| ------------- | ------------- | ---------------------------------- |
| CREATED       | VALIDATING    | 开始启动检查                       |
| VALIDATING    | INITIALIZING  | 配置、插件和能力检查全部通过       |
| INITIALIZING  | RUNNING       | 初始化及必要的健康检查成功         |
| RUNNING       | CHECKPOINTING | 开始一次 Checkpoint 阶段           |
| CHECKPOINTING | RUNNING       | 本次 Checkpoint 成功，允许继续工作 |
| RUNNING       | STOPPING      | 正常工作完成或接受正常停止请求     |
| STOPPING      | FINISHED      | 正常停止和清理完成                 |

**负责人已按 D02、D04 确认以下失败与恢复转换：**

| 当前状态                       | 目标状态   | 对应决策                        |
| ------------------------------ | ---------- | ------------------------------- |
| VALIDATING、INITIALIZING       | FAILED     | D02：启动失败                   |
| RUNNING、CHECKPOINTING         | FAILED     | D02：不可恢复的运行错误         |
| DEGRADED、RECOVERING、STOPPING | FAILED     | D02：故障处理、恢复或清理失败   |
| RUNNING、CHECKPOINTING         | DEGRADED   | D04：故障进入受限处理阶段       |
| DEGRADED                       | RECOVERING | D04：开始明确的恢复操作         |
| RECOVERING                     | RUNNING    | D04：恢复成功且重新满足运行条件 |

正常 Checkpoint 完成后可以回到 RUNNING，不代表保存失败也可以自动回到 RUNNING。失败情况必须进入已定义的故障处理路径。

### 6. 转换入口的基本契约

建议在 runtime 模块中定义 RuntimeState 和状态机对象；具体文件名可使用 `src/forgerl/runtime/state.py`。

契约包括：

- 新对象从 CREATED 开始，不通过构造参数任意指定初始运行阶段。
- 当前状态对外只读，变化统一经过转换入口。
- 转换规则使用明确允许列表，不按枚举的数值或排列顺序判断。
- 查询是否允许转换不修改状态、不产生事件。
- 真正执行转换时仍检查合法性，不能依赖调用者提前查询。
- 不合法的转换不改变原状态，也不生成表示转换成功的事件。
- 不同对象的状态彼此独立，不使用全局可变状态单例。

建议新增 InvalidStateTransitionError，继承 ForgeRLError。异常信息包含当前状态、目标状态和拒绝原因。非法请求本身不会自动把状态改成 FAILED；是否终止 Run 由外层错误策略决定。

### 7. 事件与转换结果一致

**既有约束：成功的全局状态变化需要生成 RuntimeEvent；payload 遵循 ADR-0003 的严格 JSON 规则。**

按 D05 新增通用事件类型 RUN_STATE_CHANGED，成功转换返回 RuntimeEvent；按 D06 保留开发阶段 Schema 版本 "1.0"。

建议约定其 payload：

| 字段       | 类型       | 语义               |
| ---------- | ---------- | ------------------ |
| from_state | 非空字符串 | 转换前的状态枚举值 |
| to_state   | 非空字符串 | 转换后的状态枚举值 |
| reason     | 非空字符串 | 此次转换的原因     |

沿用 RuntimeEvent 已有的 schema_version、event_id、timestamp_ns、run_id、worker_id 和 policy_version。事件记录转换时的策略版本，状态机自身不增加 policy_version。

事件 ID 使用 UUID，时间使用 Unix wall-clock 纳秒；测试可以替换模块中的生成函数，模拟生成或验证失败。耗时测量另行使用 monotonic 时间。

构造函数拒绝非字符串或纯空白 run_id；转换入口拒绝非 RuntimeState 目标、非字符串或纯空白 reason，以及布尔值、非整数或负数 policy_version。类型错误抛出 TypeError，非法值抛出 ValueError；合法枚举之间不允许的转换抛出 InvalidStateTransitionError。输入保持原值，不做隐式类型转换或空白修正。

转换规则、输入和事件构造应在提交状态变化之前完成检查。若事件构造失败，原状态保持不变。成功返回时，新状态与返回或记录的事件必须一致。

第二周只保证进程内转换结果的一致性，不承诺进程崩溃时的事件持久化、网络消息恰好一次投递或跨系统事务。日志发布失败也不能被解释为实际工作从未发生。

通用状态事件与业务事件分别定义触发条件。不能仅凭进入 CHECKPOINTING 就发出 CHECKPOINT_COMPLETED，也不能收到一次 TRAIN_STEP_COMPLETED 就自动改变全局状态。

## Confirmed Decisions

以下项目均已有负责人结论。实现、转换表和测试以结论为准；推荐与备选内容保留作为设计依据。

### 【已确认 D01】终态与同状态请求

- 推荐：FINISHED、FAILED 没有出边；所有同状态请求均拒绝。
- 备选：允许同状态请求作为幂等无操作，但需明确返回值、事件是否生成，避免重复业务事件。
- 理由：严格规则便于第二周发现调用顺序错误；未来幂等停止可作为命令层行为单独设计。
- 负责人结论：FINISHED、FAILED 没有出边；所有同状态请求均拒绝。

### 【已确认 D02】失败路径与资源清理边界

- 推荐：接受第 5 节列出的失败转换；FAILED 表示失败结果，外层通过明确的清理流程处理已创建资源，FAILED 不承诺资源已全部释放。
- 备选：必须先进入 STOPPING，完成清理后再进入 FAILED；这要求额外保存正常结束或失败结束的意图，并规定清理再次失败时的行为。
- 理由：推荐方案较小，但调用方不得把进入 FAILED 当作清理完成的证明；运行入口仍需等待清理完成或报告清理失败。
- 负责人结论：接受第 5 节列出的失败转换；FAILED 表示失败结果，外层通过明确的清理流程处理已创建资源，FAILED 不承诺资源已全部释放。

### 【已确认 D03】正常停止请求的接受阶段

- 推荐：第二周只支持 RUNNING 进入 STOPPING。CHECKPOINTING 收到停止意图时，由 Coordinator 记录，保存成功并返回 RUNNING 后再停止；保存失败按故障策略处理。
- 推荐范围内：启动期间取消、CREATED 直接结束、恢复中取消暂不提供；明确拒绝或留到生命周期设计，不能假装已经支持。
- 备选：允许更多阶段进入 STOPPING，但必须逐项定义中断后的资源清理和最终结果。
- 理由：避免在没有取消协议时声明可以中断初始化、恢复或 Checkpoint。
- 负责人结论：第二周只支持 RUNNING 进入 STOPPING。CHECKPOINTING 收到停止意图时，由 Coordinator 记录，保存成功并返回 RUNNING 后再停止；保存失败按故障策略处理。但是更多阶段进入STOPPING作为后续的可拓展方向

### 【已确认 D04】降级和恢复的来源与前置条件

- 推荐：第二周只允许 RUNNING、CHECKPOINTING 进入 DEGRADED；再按 DEGRADED → RECOVERING → RUNNING 或 FAILED 处理。
- 进入 RUNNING 前，Coordinator 必须确认初始化条件仍成立、失败操作已处置、恢复验证成功。故障发生在 Checkpoint 时，不能遗漏临时文件和发布状态检查。
- 启动失败不借恢复路径绕过初始化；严重不可恢复错误可按 D02 直接失败。
- 备选：扩大降级来源，或保留故障前状态并恢复到该状态；需要额外状态和前置条件。
- 理由：项目“任意运行状态”的描述需要收紧为可测试的来源集合；定义恢复状态不代表实现 Worker 热重启。
- 负责人结论：按照推荐来

### 【已确认 D05】状态变化事件的生成接口

- 推荐：成功转换返回一条 RUN_STATE_CHANGED 类型的 RuntimeEvent，Coordinator 收集或发布；状态机内部不调用文件、网络或任意事件回调。
- 备选：状态机保存进程内待发布事件，由调用方提取；需规定提取、清空、重复读取和内存增长行为。
- 不推荐第二周直接调用外部发布回调：发布异常会使状态变化和投递结果的关系变复杂。
- 理由：返回事件可以让转换结果直接可测，同时保持小范围实现。返回一条事件不等于保证它已被持久化或被消费者收到。
- 负责人结论：成功转换返回一条 RUN_STATE_CHANGED 类型的 RuntimeEvent，Coordinator 收集或发布；状态机内部不调用文件、网络或任意事件回调。

### 【已确认 D06】新增事件类型的 Schema 兼容性

- 当前：RuntimeEvent 的 Schema 为 "1.0"，事件类型使用受控枚举；旧消费者即使字段结构相同，也可能拒绝新事件值。
- 推荐：项目尚未发布稳定协议时，更新所有生产者、消费者、测试及 ADR-0003 的受控事件说明，保留 "1.0"，并明确这是开发阶段的契约修订。
- 备选：将 RuntimeEvent Schema 升至 "1.1" 并同步更新支持版本；仍按精确匹配规则处理，不自动兼容旧版本。
- 理由：新增枚举值并非对所有消费者透明；版本策略必须明确，不能只修改枚举却声称完全兼容。
- 实施时新增枚举值，RuntimeEvent Schema 常量保持 "1.0"。
- 负责人结论：项目尚未发布稳定协议时，更新所有生产者、消费者、测试及 ADR-0003 的受控事件说明，保留 "1.0"，并明确这是开发阶段的契约修订。

## Alternatives Considered

### 多个布尔值表示生命周期

分别维护 running、failed、finished 等标志容易形成矛盾组合，需要在每个调用点重新检查，不能集中表达合法阶段顺序，因此不采用。

### 由各模块直接写入全局状态

实现初期方便，但多 Worker 接入后会出现多个写入者，难以解释转换顺序和错误归属，因此沿用 Coordinator 统一写入的项目约束。

### 只记录事件，不维护显式状态机

普通事件枚举不表达允许的阶段转换。若从事件重建状态，还需处理事件顺序、重放、重复和持久化；这属于事件溯源架构，超出第二周需求。

### 转换时自动执行业务工作

把初始化、保存模型和清理绑定在状态对象中，会扩大依赖，使 CPU 单元测试变成执行流程测试。本 ADR 将阶段约束与具体工作分开。

### 一个状态机直接代表一个操作系统进程

一个 Run 可以跨多个进程，一个进程也可以承载多个逻辑角色。进程存活、Worker 健康和 Run 阶段的含义不同，应由各自组件维护，不共用全局状态枚举。

## Consequences

### Positive

- 生命周期规则可以集中审查并在 CPU 上测试。
- Coordinator、Worker、事件消费者之间有明确的职责边界。
- 非法转换可以保留原状态和失败证据。
- 状态变化能够使用已有 RuntimeEvent 协议进行关联。
- 第二周可以先验证规则，后续再接入真实执行、进程和恢复机制。

### Negative

- 必须先明确失败、停止和恢复语义，不能仅实现正常路径。
- 状态机只能检查阶段顺序，实际工作的成功条件仍由 Coordinator 保证。
- 事件生成与发布分开后，调用方需要负责收集、发布和处理发布失败。
- 新增事件值需要按 D06 同步协议说明和消费者。
- 未来后台 Checkpoint、并发恢复或更复杂取消语义可能需要重新设计状态集合。

## Compatibility

本决策新增 RuntimeState、RuntimeStateMachine、InvalidStateTransitionError 和 RUN_STATE_CHANGED 事件值，RuntimeEvent 的字段结构及 Schema 常量保持不变。

这是未发布稳定协议前的开发阶段契约修订；使用封闭事件枚举的消费者须同步更新，不能宣称旧消费者自动兼容。既有事件含义保持不变，例如 TRAIN_STEP_COMPLETED 仍然描述 Step 完成，而不是 Run 进入 RUNNING。

本 ADR 不定义 PID 管理、Worker 实例代次、Checkpoint 恢复标识，也不保证当前运行中断后可以仅凭状态值恢复。

## Validation

使用独立的行为测试落实已确认决策；不得仅复制实现中的转换表作为测试预期。

### 正常路径

- 新对象处于 CREATED。
- 正常启动、运行、停止和完成的路径可执行。
- RUNNING → CHECKPOINTING → RUNNING 可执行。
- 成功转换产生与新旧状态一致的 RuntimeEvent。

### 边界条件

- 同状态请求、终态请求符合 D01。
- 停止请求的来源和 Checkpoint 期间的处理符合 D03。
- 不同状态机实例的状态相互独立。
- 查询转换合法性没有副作用。
- 事件关联正确的 run_id，全局状态变化按约定使用 worker_id。
- 多条训练 Step 或心跳事件不必改变全局状态。

### 失败路径

- CREATED 不能跳过校验直接进入 RUNNING。
- 非法转换抛出专用错误，原状态不变，不产生成功转换事件。
- 启动失败、不可恢复错误和清理失败符合 D02。
- 降级和恢复路径符合 D04，不允许绕过初始化条件。
- 事件参数不合法或事件构造失败时，原状态不变。
- 事件 payload 不包含异常对象、Tensor 或其他非 JSON 值。

主体测试不依赖 GPU、子进程、真实模型、文件发布或网络服务。资源清理正确性由后续生命周期测试验证，不能只凭状态机测试声称已完成。

## Review Conditions

出现以下情况时重新评审：

- 多个调用方需要并发请求全局状态变化。
- Checkpoint 与训练并行执行，全局单一阶段不足以表达行为。
- 需要启动中取消、恢复中取消或重复停止的幂等保证。
- 引入 Worker 热重启、进程代次或多次运行尝试。
- 需要持久化事件、重放状态或跨系统事务保证。
- 插件或外部系统需要消费新增状态与事件值。
- FAILED 的清理边界无法满足真实生命周期要求。
