# ADR-0010：序列级 Reward 插件契约与部分评分失败

- Status: Proposed（框架草稿，Decision 由负责人填写）
- Date: 2026-11-13
- Deciders: ForgeRL 项目负责人
- Scope: 第四周 CPU Reward 插件的输入输出、结果校验和失败边界
- 需求状态: Required / Experimental / Deferred（由负责人按决策项填写）

## Context

第四周需要通过独立安装的外部 Reward 插件，验证 ForgeRL 的扩展协议。
仅能发现插件、展示元数据或校验配置，不能证明插件可被实际调用，也不能证明其返回值满足训练侧要求。

当前选择一个严格匹配示例：比较回答字符串与参考答案，为每条完整回答计算一个标量奖励。
它用于验证序列级评分契约，不承诺判断数学等价，也不依赖真实模型或 GPU。

### 既有代码与协议约束

- 插件发现、元数据和配置校验遵循 [ADR-0002](0002-plugin-discovery-with-entry-points.md)。
- 公共数据类型及其验证、版本和只读约定遵循 [ADR-0003](0003-typed-data-protocol.md)。
- `TrajectoryBatch.request_ids` 标识每条采样轨迹；同批必须唯一。
- `TrajectoryBatch.group_ids` 表达采样组关系，组大小约束属于算法侧。
- `TrajectoryBatch.prompt_ids`、`response_ids` 是 Token 张量，不是问题或回答的业务身份。
- SDK 已有 `PluginLifecycle` 和 `PluginContext`；Runtime 已有 `managed_plugin()`。
- `managed_plugin()` 管理初始化和清理，但执行体异常原样传播，不自动包装 `compute` 异常。
- 当前尚无 Reward 业务 Protocol、评分输入输出类型或 `plugin test` 命令。
- 现有 CLI 安装样例禁止实例化，仅验证管理命令，不是可执行的 Reward 插件。

### 本轮讨论已确认的方向

以下是会话结论的备忘，不代替负责人在 Decision 中填写选择、理由和边界：

- 使用 `request_id` 作为评分结果的唯一键；调用方保留采样组关系。
- 严格匹配得到 `1.0`，不匹配得到 `0.0`；不自动进行数学等价判断。
- 允许同批部分评分失败；保留其他回答的评分结果。
- 评分成功使用 `valid=True`；无法评分使用 `valid=False`，失败奖励采用 `None`。
- 插件不能修改输入；ForgeRL 负责校验返回结果。
- 非法返回结果导致报错，该批不得进入后续训练；不能自动修复为合法评分失败。
- 首版训练接纳策略为丢弃评分失败样本所在的采样组；第四周不实现训练过滤。
- 仅丢弃失败样本、使用剩余组员训练及其参数化，留待后续算法需求验证。

## Decision

填写方式：每项写明“选择、理由、核心约束、已知代价”，不要只写“按推荐执行”。
已确认方向可直接转写；尚未讨论的边界应明确标为待定，不默认为已支持。

### D01：评分输入与身份关联

需要回答：

- 最少需要哪些字段？分别由哪个上游提供，哪个流程消费？
- 输入采用什么类型和批量容器？为何不直接传入完整 `TrajectoryBatch`？
- `request_id` 的唯一性范围是什么？谁在构造结果字典前拒绝重复 ID？
- 空批次、空 ID、非字符串、空回答和空参考答案分别如何处理？注意区分空字符串与字段缺失。
- 调用方如何维护评分输入与原始轨迹、采样组的对应关系？

负责人填写：

- 选择：最少需要request_id，参考答案和完整回答；request_id沿用系统已有的轨迹标识，参考答案由数据集或者任务提供方提供。完整回答由rollout插件生成；系统统一组装校验后交给reward插件消费。~~输入为response_id为key，参考答案和response为value的字典~~。为方便检测错误，输入使用类型化记录序列，同时检测是否有重复标识。最初疑问：重复时简单替换并记录还是报错？讨论后确定报错，因为替换会丢失样本；而先构造成字典，重复信息可能在校验前已被覆盖。空批次等边界按下表处理。

| 边界 | 本例建议 |
|---|---|
| 空批次 | 拒绝，避免无意义调用 |
| 空或纯空白 ID | 拒绝，不自动修正 |
| 重复 ID | 拒绝，不覆盖 |
| 字段缺失、非字符串 | 拒绝，不自动转换 |
| 空回答 `""` | 允许，它可以是一次未产生内容的回答 |
| 空参考答案 | 当前数学任务建议拒绝，视为参考数据问题 |

- 理由及最简单替代方案：request_id按照契约能唯一标识采样轨迹；传入完整TrajectoryBatch太臃肿，开发者需要额外提供tokenizer和解码操作。
- 核心约束与边界：同批request_id必须唯一，生产者应尽量保证Run内唯一；ForgeRL调用插件前校验，不隐式修正输入。空回答允许正常评分，其他非法输入按表拒绝；调用方保留request_id与轨迹、采样组的对应关系。
- 已知代价：调用方需要提供完整response和参考答案，并对返回的结果校验
- 需求状态：Required。

### D02：结果结构与 `valid` 的含义

需要回答：

- 以 `request_id` 为键后，单条结果如何类型化？是否需要额外的批次包装对象？
- 评分成功、回答错误、无法评分三种情况分别允许哪些字段组合？
- ForgeRL 的通用奖励约束与本例严格匹配奖励的 `0.0/1.0` 规则如何分开？
- 返回顺序是否有意义？如何检查缺失键、陌生键和结果数量？
- 普通可变容器的所有权如何约定？是否允许返回后继续修改？

负责人填写：

- 选择：返回request_id为键，单条类型化结果为value的字典，结果包含reward、valid和error_message。最初不清楚“额外包装”：它是在结果映射外增加批次对象，用于承载Schema版本等信息，是否需要留到D06确认。回答正确reward=1.0，回答错误reward=0.0，valid均为True；无法评分时valid=False、reward=None，error_message为非空、非纯空白字符串；成功时error_message=None。~~预留-1字段，表示严重错误，但是目前想不到什么具体的应用场景~~。因此不加入该状态，无法继续执行的严重错误走异常路径。返回顺序没有意义；输出键集合必须与输入ID集合完全相等，不能只检查数量。插件构造结果，不允许返回后继续修改。
- 理由及最简单替代方案：valid区分回答不正确与无法评分；仅返回失败标记或只写日志无法让ForgeRL知道原因，因此增加error_message。诊断文本不用于判断重试等机器策略，当前不增加错误码枚举。
- 核心约束与边界：valid必须是布尔值；有效reward必须是有限浮点数。0.0/1.0是本例规则，不限制所有Reward；本例严格比较原始字符串，不去空格或转换数值。失败结果缺少原因等非法组合由ForgeRL拒绝，不自动修复。
- 已知代价：需要校验字段组合及完整键集合；外层包装与版本策略仍待D06确认。
- 需求状态：Required。

### D03：部分失败与整批失败的边界

需要回答：

- 哪些具体错误可隔离到单条样本，哪些错误必须终止整批调用？
- 单样本错误由插件还是调用方捕获？谁负责继续处理后续样本？
- 初始化失败、编程错误、中断与资源耗尽是否允许转成 `valid=False`？
- 如何保留可定位到插件和 `request_id` 的失败原因？现有日志是否足够？
- 严格字符串比较没有自然的评分故障时，如何通过测试替身或故障注入验证部分失败？

负责人填写：

- 选择：某条样本遇到插件明确支持处理的评分故障，valid=False隔离单条；初始化失败、编程错误或者用户中断走异常路径，由ForgeRL做插件生命周期管理；ForgeRL校验输出缺失键、NaN、非法字段组合，出错中止整批调用；内存耗尽等资源故障终止当前调用。~~初始化失败等尚不明确应该转成valid=False还是插件raise Error~~插件负责识别可隔离的单样本失败；对约定的可恢复异常进行局部捕获，生成失败结果后继续处理。其他异常向外传播。
- 思考补充：最初考虑插件自行记录诊断，但日志不一定传到ForgeRL。因此通过error_message返回原因，ForgeRL在全部输出校验通过后关联插件名、request_id和阶段统一记录；第四周先向标准错误展示，不承诺写入日志文件。插件可补充调试日志，日志不作为结果传输协议。
- 理由及最简单替代方案：整批失败更简单，但会损失其他成功评分；局部隔离保留这些评分，同时不能用宽泛捕获掩盖编程错误。
- 核心约束与边界：异常已抛出时，必须局部捕获才能继续后续样本；正常返回失败状态时无需捕获。初始化失败、中断和资源故障不得转换成valid=False；整批异常不承诺抢救尚未返回的结果。
- 已知代价：需要明确可恢复故障范围。严格比较没有自然的评分故障，使用测试替身模拟中间一条失败，检查后续样本仍被处理；不向正式插件增加故障开关。
- 需求状态：Required。

### D04：校验、执行与清理的责任边界

需要回答：

- 输入校验、插件调用和输出校验的顺序及负责方分别是什么？
- 整个输出通过校验前，是否允许向下游交付部分结果？
- 如何复用现有生命周期？执行异常与协议违规分别使用什么错误，在哪个边界转换？
- 业务调用失败后仍需怎样清理？清理也失败时保留哪个原始错误？
- 哪些只读约束由数据结构保证，哪些依赖约定与测试？

负责人填写：

- 选择：1.配置先于实例创建校验；ForgeRL校验输入后调用已初始化插件，再校验全部输出，生命周期复用managed_plugin()。2.全部输出校验通过前，不允许向下游交付部分结果。
- 错误转换：最初不清楚“在哪个边界转换”，现明确为由调用或校验发生的位置统一报告错误：compute调用边界将未处理的普通执行异常转成PluginExecutionError并保留异常链；输入/输出校验边界报告ProtocolViolationError。已有明确分类的ForgeRL错误不重复包装，中断保留原语义，资源故障不得降级成单样本失败；输出校验位于执行异常包装范围之外。
- 清理：最初不清楚业务失败后为何还需清理；失败不会自动关闭已经取得的资源。退出插件使用范围时由managed_plugin()尝试shutdown()，不要求每批都初始化和关闭。主错误与清理同时失败，保留主错误并另记清理异常；只有清理失败则报告关闭失败，不将其写入某条样本结果。
- 只读：最初认为插件部分需要完全由数据结构保证；现采用不可变记录减少误修改，同时由契约要求调用方和插件将数据视为只读，插件返回后不得继续修改结果容器，并通过测试检查。冻结外层记录不等于嵌套容器也不可变。
- 理由及最简单替代方案：复用现有错误类型与生命周期，分别保留执行失败和协议违规语义；仅靠类型标注或插件自检不足以保证边界正确性。
- 核心约束与边界：先完整校验再交付；清理不能掩盖主错误；只读约定不宣称提供任意插件代码的强制隔离。
- 已知代价：增加边界及故障测试，当前不引入深拷贝或进程隔离。
- 需求状态：Required。

### D05：评分结果与训练接纳策略

需要回答：

- 为什么保留成功评分，不代表这些评分都可以直接进入训练？
- 谁按采样组过滤数据？为什么 Reward 插件不负责整组丢弃？
- 如何避免把同一道题跨轮次的不同采样组一起丢弃？
- 当前哪些仅为后续训练侧约定，第四周不实现什么？
- 什么时候才值得增加“丢弃样本 / 丢弃采样组”的配置？还需补充哪些算法约束？

负责人填写：

- 选择：Reward保留同批成功与失败的评分，后续训练侧按当前批次的采样组丢弃失败样本所在整组；插件不负责训练过滤，第四周也不实现该过滤。
- 理由及最简单替代方案：最初考虑仅丢弃失败样本以保留更多数据，但剩余组大小会变化，需要先明确算法如何计算组内统计与Loss权重。因此首版保持固定组大小，不能将失败reward补零。
- 核心约束与边界：同一道题不同轮次的采样组相互独立，不能按题目文本统一丢弃，也不能把坏group_id全局传播到后续批次。首版训练侧要求组完整位于当前批次，只在该批次内按group_ids过滤；跨批次拆组暂不支持。
- 已知代价：整组过滤会浪费其他成功评分。仅当指标显示该损失值得优化、算法支持不完整组且有对照实验时，才增加“丢弃样本/采样组”配置；需先定义最小有效组大小、有效样本的均值/标准差、单样本和零方差处理、组间Loss权重、轨迹字段同步过滤及空批次行为。两种过滤都可能改变数据分布，不能假定保留更多样本一定更好。
- 需求状态：评分结果保留为Required；训练过滤留到算法阶段，部分组训练及配置为Deferred。

### D06：公共接口、版本与本周范围

需要回答：

- 输入输出类型与业务 Protocol 分别放在哪里？外部插件允许依赖哪些公共模块？
- 如何在类型化结果映射与 ADR-0003 的顶层协议要求之间保持一致？
- 新协议如何声明 Schema 版本？是否影响 SDK API 版本，依据是什么？
- 本周一致性测试覆盖哪些能力？Checkpoint、GPU、Token 级奖励是否在范围内？
- 如何证明 SDK 与测试入口完成后，新增外部插件只需安装包，无需再改主仓库？

负责人填写：

- 选择：放在sdk中，数据记录放在schemas.py，RewardPlugin行为Protocol放在rewards.py，并从SDK公共入口导出。输入暂沿用D01的类型化记录序列，不新增批次输入对象；是否需要输入包装仍待商榷。输出使用RewardOutput对象，包含schema_version和以request_id为键的结果映射；每条RewardResult必须包含reward、valid、error_message，不能只有奖励而没有失败信息。
- 思考补充：最初认为不影响Schema和SDK API版本；现区分为既有数据Schema保持不变，新RewardOutput拥有自己的字符串版本“1.0”，只接受精确匹配。SDK尚处开发阶段，API版本暂保持“1.0”，这是新增的未稳定发布契约，不代表旧SDK已有Reward业务能力。输入序列作为本次明确的进程内契约，不预设尚未确定的批次输入Schema；若新增输入对象，再定义其独立版本。
- 理由及最简单替代方案：不为待定输入包装提前增加公共类型；输出对象统一承载版本及逐样本错误信息。Protocol描述接口但不自动检查返回值，ForgeRL仍需运行时校验。错误信息由插件返回、ForgeRL统一记录，不重复定义批次级错误字段或通用错误枚举。
- 核心约束与边界：外部插件依赖SDK公共类型及自身依赖，不依赖Runtime私有实现。第四周覆盖CPU序列级评分、部分失败、边界校验、生命周期及外部安装一致性测试；Checkpoint、GPU、Token级奖励、多进程和训练过滤不在本周实现范围。
- 已知代价：新增输出协议与校验测试，但不修改既有TrajectoryBatch语义。先固定SDK和测试入口，再在独立环境安装外部插件，从仓库外运行plugin test；不修改主仓库、不增加插件名称分支、不调整PYTHONPATH。完成代码工作先交付SDK与评分执行切片，外部仓库和CLI一致性入口随后推进，不能提前声称第四周全部验收完成。
- 需求状态：SDK契约与CPU执行切片为Required；批次输入对象待评审，其他超出本周能力为Deferred。

### 示例数学插件的可配置规则（2026-11-14，Required）

- 思考过程：最初固定为严格匹配，因此空配置足够；随后需要让同一插件可选数值相等，增加唯一配置项match_mode=strict/numeric，默认strict，拒绝未知配置。不增加strip或容差参数。
- 选择：严格模式比较原始字符串；数值模式只接受完整的整数、小数、整数分数和科学计数法文本，允许非最简分数，拒绝所有空白、零分母、NaN/Infinity、Unicode数字及一般表达式（例如sqrt(4)、1+1）。分子与分母只能是带可选正负号的整数；小数允许.5、2.等形式。
- 最简单替代方案：浮点转换会使大整数和高精度小数误判相等；完整表达式求值超出当前需求。因此先校验语法，再用Fraction精确比较，不执行表达式，1/3不等于0.333333。
- 核心不变量：不把非字符串强转成字符串；非法回答是正常零分而非评分故障。空参考答案在两种模式报协议错误，其他非法参考答案在数值模式报协议错误。结果保留原始request_id，不修改输入或以前返回的结果。
- 代价及重新评估条件：任意精度仍受Python整数字符串转换限制和资源约束；需要近似比较、数学函数或公式求值时，重新定义规则并做对照测试，不自动扩大语法。
- 实现：examples/math_reward独立发行包，通过entry point发现，插件仅导入公开SDK；目前位于主仓示例目录，尚未创建独立Git仓库。
